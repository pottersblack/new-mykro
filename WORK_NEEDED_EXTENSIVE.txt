3) PRIMARY REMAINING WORKSTREAMS

WORKSTREAM A — Final Live Runtime Validation (Highest Priority)
---------------------------------------------------------------
Goal:
- Prove current code behaves correctly in the running process, not just in source
  or in-process test client contexts.

Tasks:
1. Verify active process ownership for port 5000 before tests.
2. Validate endpoint matrix one-by-one (avoid long chained commands):
   - GET  /api/health
   - POST /api/start      with model payload (mykro-large and mykro-small)
   - POST /api/stop
   - POST /api/completion with short deterministic prompt
3. Confirm response codes, schema, and content shape consistency.
4. Repeat once after full restart to verify cold-start stability.

Acceptance criteria:
- 2 consecutive passes without 404/500 for core control endpoints.
- Completion endpoint returns expected JSON structure and non-empty response.
- No fallback text path is triggered in normal chat operation.


WORKSTREAM B — Browser/UI Functional Validation
-----------------------------------------------
Goal:
- Confirm the neural UI interaction path is stable for real user actions.

Tasks:
1. Launch Web UI and perform Start/Stop/Reload actions from UI controls.
2. Submit chat prompts and verify no fallback synthetic response appears.
3. Confirm status banners/labels correctly reflect backend state transitions.
4. Validate model switch interactions (large/small/auto where exposed).

Acceptance criteria:
- UI buttons map to successful backend actions.
- No route errors in browser dev console for model-control actions.
- UX remains responsive during server transition periods.


WORKSTREAM C — Startup Reliability and Process Hygiene
------------------------------------------------------
Goal:
- Ensure repeatable startup/shutdown behavior and eliminate stale-process ambiguity.

Tasks:
1. Standardize launch entrypoint for operator workflows (prefer one canonical script path).
2. Add/confirm pre-launch cleanup logic:
   - detect occupied target ports
   - identify stale Python/Flask processes
   - clear or report conflicts before start
3. Add/confirm post-launch readiness checks with bounded retries.
4. Confirm graceful shutdown stops gateway + model server processes cleanly.

Acceptance criteria:
- One-step startup reliably reaches healthy state.
- One-step shutdown reliably releases ports.
- No ghost/stale listeners after stop.


WORKSTREAM D — Logging, Observability, and Fast Triage
------------------------------------------------------
Goal:
- Make failures obvious and quickly diagnosable.

Tasks:
1. Normalize key logs (web_ui, gateway, model server) with timestamps + severity.
2. Ensure errors include route, payload shape summary, and upstream target info.
3. Add a minimal startup summary block (what started, where, and health result).
4. Add a focused troubleshooting section to README for common local failures.

Acceptance criteria:
- Any failed call can be traced within <= 2 minutes from logs.
- Common issues have clear next actions in docs.


WORKSTREAM E — Regression Tests for Route Contract and Startup
--------------------------------------------------------------
Goal:
- Prevent recurrence of endpoint drift and startup regressions.

Tasks:
1. Add/update tests for:
   - /api/start model ID resolution behavior
   - /api/stop behavior in running and non-running states
   - /api/completion basic proxy success path
2. Add startup smoke test assertions for expected ports/routes.
3. Add frontend route contract test if feasible (static check or lightweight integration).

Acceptance criteria:
- Test suite catches route drift before manual runtime testing.
- Smoke tests fail loudly on missing endpoint mappings.

6) RISK REGISTER
====================================================================
Risk 1: Running code differs from edited source (stale process/image)
- Impact: false negatives/positives during validation
- Mitigation: always identify process PID + executable path before tests

Risk 2: Route drift between frontend and backend
- Impact: UI controls silently degrade
- Mitigation: contract tests + single source-of-truth route constants

Risk 3: Port collisions from old processes
- Impact: startup appears successful but talks to wrong process
- Mitigation: preflight kill/report + startup ownership checks

Risk 4: Multi-step command interruptions in terminal
- Impact: ambiguous diagnostics
- Mitigation: short single-purpose checks and explicit pass/fail logs

Risk 5: Model warmup latency interpreted as failure
- Impact: flaky startup probes
- Mitigation: readiness polling with realistic timeout windows
